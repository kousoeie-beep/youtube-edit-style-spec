# 再実装検証プロトコル（正本）

**このファイルは何か**: 「yaml だけを読んで作り直し、実測し、目視する」検証の手順書。
R8〜R11 の4周で収束したものを、口伝から文書へ移した。
**エルメス（Hermes Agent）へチューニングを引き継ぐ場合、渡すのはこの手順書と `lint.py` / `overlap_qc.py` / `measure.py`。**

## 0. この検証が何を測っているか

測っているのは **「yaml のフィールドだけで、実装者が一意に組めるか」** である。
散文の説明は読んでよいが、**実装の根拠には使わない**。散文は
「フィールドと食い違っていないか」を探す材料としてのみ使う。

**だから実装は毎周ゼロから書き捨てる。** 共通のレンダラを使ってはいけない。
再実装が消えると、この検証は何も測らなくなる。

## 1. 絶対規則

- **git 操作は一切しない**（add / commit / push / checkout / stash）
- **yaml 本体を書き換えない**。作業コピーは scratchpad に置く
- `.raw/` は読み取り専用
- API キーの値をログ・報告書・チャットに出さない（存在確認は `[ -n "$KEY" ]`）
- 報告書は **節ごとに追記する**。まとめてから書くと、途中で落ちたときに全部消える
  （R10 で実際に2本落ち、追記式だった1本だけ509行の実測が残って判定まで回収できた）

## 2. 先に読むもの

1. `style-learning/schema.md` — 規約の正本。**末尾の追記から読む**（新しいものほど重い）
2. `qc-gates.md` — QC が原理的に見られないもの
3. `environment-notes.md` — レンダリング要件
4. 前周の報告書

## 3. 手順

### (a) 実装 — 毎周ゼロから
yaml を pyyaml でパースし、**フィールド値だけ**からレイヤーを組む。
25秒程度のクリップを作る。`work/<name>/assets/` にベース映像と音声を**先に置く**
（無いと ffmpeg が落ちるが、`set -e` で成功メッセージが出ないだけになり原因が分かりにくい）。

### (b) 対照窓
規約を**あえて破った窓**を作ってよい（破ったときに何が起きるかの記録になる）。
ただし:
- **時刻をビルドスクリプトと報告書の両方に明記する**
- 本編クリップと時間で完全に分離する
- **QC の config を本編用と対照窓用に分ける**（本編が単独で exit 0 になるかを判定するため）

これを怠ると、次に読む人が**対照窓の FAIL を実害と読み違える**（実際に起きた）。

### (c) QC
```bash
uv run --with pillow --with numpy python3 ../overlap_qc/overlap_qc.py \
  --config configs/<name>.json --out-json work/<name>/overlap_qc_result.json
```
- 終了コード: `0`=PASS / `1`=FAIL / `2`=NOT_INSPECTED または PARTIAL
- **`element_count` が、生成レイヤー数から `layer_kind: video` および明示的な検査除外レイヤーを差し引いた「検査可能レイヤー数」と一致しなければ、QC は信用しない**
- `layer_kind: video` の role は検査対象外。**目視が唯一の担保**

### (d) 実測
```bash
uv run --with pyyaml python3 verify/measure.py --boxes styles/<style>.yaml
uv run --with pillow --with numpy python3 verify/measure.py --work work/<name> --name <name>
```
- **導出は箱基準（`--boxes`）で行う。** 実装者が読むのは `size` の箱である
- インク実測（`--work`）は「箱の宣言が実物と合っているか」の照合に使う
- **箱とインクは一致しない**（箱は centerY に対称、インクは影とグリフで非対称）。
  インク基準で16px取ると箱では4pxになる——R10 でこれを踏んだ

### (e) 目視
最低6点。**QC が緑でも必ず見る**。とくに:
- `layer_kind: video` を含むフレーム
- グロー／ぼかしを持つ要素（alpha 閾値で QC の網をすり抜ける）
- 全画面カードの上に何か乗っていないか
- 対照窓（破った側で何が壊れるかを記録する）

### (f) 判定と報告
下の §4 の定義で **可 / 不可** を明記する。

## 4. 判定基準

**可** = 次の全部を満たす:
1. yaml のフィールドだけで一意に組めた（発明した値が0件）
2. 本編 config の QC が exit 0
3. 4辺検算 NG が0件、role間のすきまが全て16px以上
4. 目視で破綻なし
5. 実測値が yaml の宣言と一致する（宣言16pxに対し実測9px、は不可）

**1つでも欠けたら不可。** 「ほぼ可」は書かない。

## 5. 報告に必ず書くこと

- **数値には実測の出所を添える**（どのPNG・どの座標計算・何字の何px）。
  「実測」と書くだけでは実測にならない——測った文字列・px・字数の3点が要る
  （schema.md R10追記。同じ周に足した2つの定数で、出所を書いたほうだけが効いた）
- **自分の実装ミスと yaml の欠陥を分けて書く**（節を分ける）。混同しかけたらそう書く
- 変更ごとに「効いた / 効いていない / **効いたが別の破綻を作った**」
- **とくに探すもの**: 「値を動かしたのに、その値から導出された別の値が追随していない」組。
  R9〜R11 の高深刻度欠陥はほとんどこの型だった

## 6. 修正案の書き方

フィールド名・数値・**導出**の3点セット。導出が無い数値は次の周で必ず外れる。

```
`person_status.centerY`: 0.135 → 0.165
  導出: chapter_tag 箱の下端 100.5px + 余白16px + 自分の半分55px = 171.5 → 0.1588
        安全側で 0.165（= 178.2px、上端120.2px、クリアランス19.7px）
```

## 6.5 yaml を編集するときの道具

`verify/yamledit.py` の `set_field()` を通す。直接書き換えない。

```python
import sys; sys.path.insert(0, "verify")
import yamledit as Y
Y.set_field("styles/<name>.yaml", "<role>", "<key>", "<value>", "<注記>")
```

**この関数の存在理由は「重複キーを作らないこと」だけ**である。
YAML は同名キーを黙って後勝ちにするので、素朴に挿入すると
**さっき書いた修正値が消える**（2026-07-27 に同じ事故を8回作った）。

置換時は継続コメント行ごと差し替える。残すと、新しい注記の下に
前の注記の後半だけが宙に浮く。

## 7. 周回の閉じ方

修正を適用したら **`lint.py` を流して違反0を確認してから**次の周に入る。
lint に無い規約は守られない——規約を足したら、その周のうちに検査も足す。
