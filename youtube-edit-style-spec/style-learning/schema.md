# スタイル学習: スキーマ・色ロール・登録前ゲート・予約席

**このファイルは何を扱うか**: 抽出する編集パラメータの一覧、色の共通ボキャブラリ（7ロール）、数値目標を書く前の検算義務（登録前ゲート）、自由記述に新装置が出た際のrole確保ルール（予約席）、新規スタイルyamlに必須の7項目。
**いつ読むか**: スタイル学習の手順3（抽出パラメータの決定）およびyamlを新規登録・更新するとき。登録後の整合性チェックは [consistency-check.md](consistency-check.md) を参照。

3. 抽出する編集パラメータ（スキーマは `wiki/AI対話/kousuke/スキーマ_スタイル記述v1.md` 準拠）: format/palette（HEX）/telop_layers（層構成・配置・色ロール）/animation（入退場の種類と速度）/cuts_per_min/挿入素材の頻度と種類/BGM・SFX方針/構成（フック・章立て・CTA）

### 【色の共通ボキャブラリ】配色は7ロールで表す（AKARI Videoから移植・2026-07-27）

**現状の問題**: `brand_hex` は色の平坦なリスト＋散文の説明で、「どの色がどの役割か」が
構造化されていない。17スタイルをまたいだ配色の比較・差し替えができず、
実装者が毎回 `emphasis_roles` の日本語を読んで解釈している。

AKARI Video は36件のテロップテンプレート**全部**に役割ベースの色命名を適用済み。
これをそのまま共通ボキャブラリとして採用する（実際の使用頻度順）:

| ロール | 用途 | akariでの出現数 |
|---|---|---|
| `color_text` | 文字色（地の文） | 103 |
| `color_bg` | 背景・座布団・帯の地色 | 83 |
| `color_shadow` | ドロップシャドウ | 82 |
| `color_accent` | 強調・アクセント（1スタイルに複数可） | 55 |
| `color_stroke` | 縁取り（袋文字のフチ） | 41 |
| `color_primary` | ブランド主色（ロゴ・バッジ等） | 24 |
| `color_glow` | グロー・ネオン効果 | 10 |

**書き方**（`brand_hex` は出典情報を持つので残し、`color_roles` を併記する）:
```yaml
palette:
  brand_hex: ["#C1AC20(大型見出し、ヒストグラム実測)", ...]   # 出典つきの生データ。従来通り
  color_roles:                                                  # 役割マッピング（新規）
    color_text: "#FFFFFF"
    color_bg: "#000000"
    color_accent: ["#C1AC20", "#F7E24A"]    # 複数可
    color_stroke: "#000000"
    color_shadow: "rgba(0,0,0,0.4)"
    color_primary: "#6BCD6A"
    color_glow: null                          # 使わないロールは null で明示
```

**利点**:
- スタイルをまたいで「このスタイルのaccentを別スタイルのものに差し替える」が機械的にできる
- 実装者が散文を読まずに色を引ける
- **使わないロールを `null` で明示**することで「未定義」と「意図的に不使用」が区別できる

**【2026-07-27 適用時に判明した構造的欠落】`color_shadow` が15/15スタイルで null だった。**
[environment-notes.md](../environment-notes.md) には「**ドロップシャドウ常時（offset 4,4px・blur 3・不透明度40%）**」という
確定仕様（2026-07-11チューニング）があるにもかかわらず、**どのスタイルも色を記録していない**。
実装者は毎回この確定仕様を探しに来るか、独自判断していたことになる。
→ **全スタイル共通のデフォルトとして以下を規定する**（スタイル側で上書きしない限りこれを使う）:
```yaml
color_shadow: "rgba(0,0,0,0.4)"   # 全スタイル共通デフォルト。
  # SKILL.mdの確定仕様（offset 4,4px・blur 3・不透明度40%）に対応する色。
  # スタイル固有のシャドウ色を実測した場合のみ上書きする
```
他のnull分布も記録しておく（**nullが多い＝そのロールの規約が未整備という指標になる**）:
`color_glow` 14/15・`color_primary` 12/15・`color_stroke` 8/15・`color_accent` 4/15・
`color_text` 2/15・`color_bg` 1/15。
**`color_stroke` が8/15 null なのも要注意**（「黒フチ12px」という確定仕様があるのに色が未記録）。

### 【登録前ゲート】数値目標は「達成可能か」を検算してから書く（AKARI Videoの契約設計から移植・2026-07-27）

OSS `AkariLabs/akari-video` の `contract-2026-07-22-render-basics.md` は
**「done = 出力ファイルに現れる。全項目、実レンダリング出力の機械検証を受け入れ条件とする」**
を大原則にし、数値目標ごとに「出力検証の方法」を契約の時点で義務化している。
こちらは**実装後に「実は達成不能だった」と気づく**運用になっていたため、この考え方を移植する。

**新規スタイル登録時、数値目標を書く前に必ず以下を検算する**:

| 目標 | 検算式 | 不合格なら |
|---|---|---|
| LUFS と LRA の組 | 交換関係（LUFSを1LU上げるとLRAが約0.9LU減）で両立するか | **どちらを優先するかをyamlに明記**する。両方を目標として書かない |
| LRA | 素材のLRA上限を超えていないか（`ffmpeg -af ebur128` で事前測定） | 「素材の限界により達成不能」と明記する |
| 無音率 | 目標率 ≧ 0.5秒 ÷ 検証クリップ長 か（30秒なら1.67%） | **必要クリップ長 = 0.5 ÷ 目標率 秒**を併記する |
| cuts_per_min | オーバーレイ誤検知を除いて測れるか | 「クリーンベースで測る」旨を併記する |

> LUFS/LRAの交換関係の実測データと無音率の測定下限の詳細は [audio-pipeline.md](../audio-pipeline.md) を参照。

**さらに `verify` フィールドを数値目標の隣に必須で置く**（AKARIの「出力検証」列と同型）:
```yaml
audio:
  voice_lufs_target: -14.0
  lra: 5.7
  verify:
    lufs: "ffmpeg -af ebur128 で最終ファイルを実測、±1LU以内"
    lra: "同上。素材LRAが目標未満なら『達成不能』であって『測定不能』ではない。区別して書く"
    無音率: "silencedetect -35dB/0.5s。クリップ長30秒なら下限1.67%"
```
**単体の値ではなく「値同士の関係」を検証する**という視点が要点
（AKARIの `validate-edit.mjs` が兄弟フィールドを突き合わせるのと同じ発想）。

### 【予約席】自由記述に新しい装置が出たら、その場でroleを確保する（同上から移植）

AKARIの契約は末尾に「次段（本契約のスコープ外）」を置き、**将来拡張の席を先に名前だけ確保**している。
こちらで繰り返し起きた「variant_splitに書いた装置に対応するroleが無く実装者が独自判断」は、
この予約席の欠如そのものだった。

**運用ルール**: n増や変種確定で**自由記述に新しい装置名が出てきたら、その場で**
1. `telop_layers` に対応するroleを追加登録する、または
2. `予約_未定義role:` セクションに装置名だけ書き「次回のn増で定義する」と宣言する

**自由記述にだけ書いて何も予約しないことを禁止する。**
既存の自己点検grepが「古い記述が残っていないか」の**事後検査**なのに対し、
予約席は「新しい装置が登場した瞬間に名前を確保する」**事前防止**。両方を回す。

**スタイルyamlに必ず含めるべき項目（2026-07-25の適用検証で欠落が判明。以後の新規登録で必須化）**:

適用検証（step5）を実施したところ、既存yamlに以下の欠落があり実装者の解釈に委ねられていた。**新規スタイル登録時はこの7項目を必ず埋める**（実測できなければ「未計測」と明記した上で採用すべきデフォルト値を書く）:

1. **entrance/exitの秒数**: `hard_cut` とだけ書かず `fade=0` など数値で書く。「ハードカット」が0秒なのか1-2フレームのクロスフェード許容なのかが不明だと実装がブレる
2. **captionのフォントサイズ・フチ幅・不透明度**: 基準プリセット既定値には「フォント92／黒フチ12px」という確定数値があるが、新規スタイルには無いことが多い。無いとスタイル間で一貫性のない数値が採用される
3. **telop_layersのz-order（重なり順）**: 「リスト順＝重なり順」という規約がどこにも明記されていない。コールアウトがsidebarより上に来る必要がある等、実装時に自明でない。**z-orderを明示フィールドとして持たせる**
4. **dual_mode（モード切替型）スタイルでのcaption挙動**: モードAとモードBのどちらでcaptionを出すかが未定義だと、カードとキャプションが衝突する。モードごとの表示規則を書く
5. **`position` の解釈規約を守る**（2026-07-26 documentary_immersive検証で欠落が判明）。
   `{centerX, centerY}` が何を指すかが未定義だったため、**幾何中心**として実装したところ
   2行字幕が下端で約18px見切れた。以下を全スタイル共通の規約とする:
   - **`centerX` は要素の水平方向の中心**（これは自明）
   - **`centerY` は「1行の場合は幾何中心、複数行の場合は最終行の下端が `centerY + 半分` を
     超えないように上へ繰り上げる」**＝実質「下端が画面外に出ないことを優先する」
   - **黒フチ・ドロップシャドウの太さを含めた実描画bboxで判定する**（フチ12pxを忘れると見切れる）
   - 実装前に `centerY × 1080 + 要素高さ/2 + フチ幅 ≤ 1080` を検算すること
6. **同時表示される要素同士のY座標は、実描画高さを足して衝突しないか検算する**（同上の検証で実害）。
   documentary_immersiveは名札(centerY 0.86)と字幕(centerY 0.90)が**43px差しかなく構造的に衝突が確定**
   していた（overlap_qc FAIL・pixel_collision 99.8%を実測。z_order上は字幕が前面のため
   **名札が字幕表示中は完全に不可視**になっていた）。**yamlに書いた座標が実際に共存できるかは、
   登録時に検算しないと分からない**。
   ```
   要素Aの下端 = centerY_A × 1080 + 高さA/2 + フチA
   要素Bの上端 = centerY_B × 1080 - 高さB/2 - フチB
   → 下端A < 上端B でなければ衝突する
   ```
7. **変種固有の装置には必ず対応する `telop_layers` の role を作る**（2026-07-25の適用検証で判明した、より根本的な欠陥）。`variant_split` の自由記述に「6点セット」等を書いても、上部の構造化スキーマ `telop_layers` にroleが無ければ**実装者がrole・z_order・entrance/exitを独自判断するしかなくなる**。実例: `documentary_startup_journey` は変種の6点セットのうち「Q.質問カード」「人物ステータス」「CTAバナー」の3つにroleが無く、しかも `nameplate` は番組ロゴに割り当て済みだったため**人物の名前テロップに使えるroleが存在しなかった**（`question_card` / `person_status` / `cta_banner` を追加して解消）。
   → **チェック方法**: variant_splitに書いた装置を一つずつ指差し、対応する `telop_layers` エントリがあるか確認する。**構造化スキーマと自由記述が非同期になっていないか**を登録前に必ず点検する
## 文字数制約は散文でなく `max_chars` に書く（2026-07-27 追加・実害あり）

**roleの説明に「短文」「一言」「キーワード級」「抜き出し型」「1-2文字」等と書いたら、
必ず `max_chars` を併記する。** 散文だけの制約は実装者に届かない。

実害: `documentary_immersive` のB3 captionは「キーワード級の短文、フルセンテンスでは
なく抜き出し型」と散文で書かれていたが `max_chars` が無かった。改修後のyamlだけを読んで
再実装した検証で**2行字幕が生成され、person_nameplateを99.7%覆い隠した**。
座標をどう動かしても解決しないことが実測で確定している（status card下端687〜字幕上端815の
128pxに高さ124pxの名札は入らない）。**真因は座標ではなく機械可読な制約の欠落だった。**

- 値が実測できるなら実測値を書く（例: フォント92・折返し幅900pxで9字=843pxが1行の上限）
- **実測できないなら `max_chars: 未計測` と明記する**。書かないと「制約なし」と読まれる
- 「推奨」なのか「守らないと破綻する」のかを注記で区別する

## 排他と変種は散文でなくフィールドで書く（2026-07-27 追加・実害あり）

`max_chars` と同じ構図の欠陥が「同時表示の可否」で起きている。掃引の結果、
**`mutually_exclusive_with` は15ファイル中1ファイル（educational_explainer）にしか無く、
残り14ファイルの排他制約はすべて散文**だった。`wipe_explainer` は
「**同時に出してはいけない**」と太字で書きながらフィールドを持っていない。

危険なのは**座標が一致している排他ペア**である。排他前提が破られた瞬間に100%重畳する。
実際 `ai_biz_pitch` の shock_keyword と positive_keyword は
position が完全一致（0.5, 0.72）・z_order も同値のまま、排他は散文だけで担保されている。

### `mutually_exclusive_with`

| 値 | 意味 |
|---|---|
| `all` | **表示中は他の全レイヤーと同時表示しない**（全画面カードはこれ） |
| `<role名>` | そのroleと同時表示しない |
| `[<role名>, ...]` | 複数と同時表示しない |

同一role名が2エントリある場合（変種違い・モード違い）は、両方に
`mutually_exclusive_with: <自身と同じrole名>` を書く。「もう一方のエントリと排他」の意味になる。

### `variant`

`【変種: B2のみ】` のような**日本語コメントは変種スコープを表現できない**。
パーサから読めるよう、変種に属するレイヤーには `variant: <変種ID>` を書く。
省略時は「全変種で共通」を意味する。

### 書かない場合の意味

**フィールドが無い＝「排他ではない（同時に出てよい）」と読まれる。**
排他なのに書かなければ、実装者は同時に出す。未検証なら
`mutually_exclusive_with: 未検証` と明記して判断を保留させること。

## `entrance`/`exit` の秒数は `fade_sec` フィールドに書く（2026-07-27 追加）

本ファイルは既に「`hard_cut` とだけ書かず `fade=0` など数値で書く」を必須にしているが、
**掃引時点で秒数フィールドは15ファイル中ゼロ件**、値はすべてコメント文字列だった。
`documentary_narrated_jp` は実装検証で採用済みの `fade_sec: 2.0` をコメント本文に
書いており、パーサから見えない状態だった。

- `entrance_sec` / `exit_sec` を数値で書く（ハードカットは `0`）
- 未計測なら `未計測` と文字列で書く。**書かないと「0（即時）」と読まれる**

## `max_chars` は「1行の上限」。折返し幅も併記する（2026-07-27 追加）

再実装検証で **`max_chars` が「1行あたりの上限」なのか「テロップ全体の上限」なのかが
どこにも書かれておらず、解釈次第で下流の衝突判定が全部変わる**ことが判明した。

- **定義: `max_chars` は1行あたりの上限とする。**
- **`max_width_px` を必ず併記する。** `max_chars` はフォントサイズと折返し幅が決まって
  初めて意味を持つ派生値であり、単体では脆い。フォントを変えた瞬間に無意味になる。
- 先行事例は `business_talk` の `max_width_px`。同時表示する相手によって折返し幅を
  変える（サイドバーのみ628px / サイドバー+名札484px）ところまで表現できている。
  **この形式を正とする。**

実害の例: ai_biz_pitch は `base_caption` に `max_chars: 20` / フォント92 を持つが折返し幅が無く、
「1行の上限」と解釈すると実測幅 **1858px＝画面幅の96.8%**（左右余白29px）になる。
この解釈の違いで、画面下部の他要素との衝突が出るか出ないかが変わる。

## 意図的な重なりは `intentional_overlap_with` で宣言する（2026-07-27 追加）

ハイライトマーカーのように**設計上わざと重ねる**装置がある。宣言が無いと
overlap_qc が毎回FAILを出し、**本物の衝突がノイズに埋もれる**。

- `intentional_overlap_with: <role名>` を書く
- 併せて、その装置が相手の**直下**に来るのか直上に来るのかを注記する
  （ai_biz_pitch の highlight_marker は z_order=1 と base_caption=4 の間に z=2/3 が実在し、
  「1枚のPNGに焼き込め」という実装指示と z_order 定義が**同時に満たせない**状態だった）

## `color_roles` の null は3つの意味を混同している（2026-07-27 追加）

再実装検証で、`null` が**「その色を使わない」「測れていない」「まだ書いていない」の
3つを区別できていない**ことが判明した。実装者は結局散文を読みに行くしかなく、
色ロールを作った意味が失われていた。

**三値で書き分ける:**

| 値 | 意味 | 実装者がすること |
|---|---|---|
| `"#RRGGBB"` / `"rgba(...)"` | 確定値 | そのまま使う |
| `"none"` | **意図的にその色を使わない**（例: 縁取り無しが意匠） | 描かない |
| `"未計測"` | 測れていない。あるかもしれない | 保守的な既定値を使い、実素材で確認する |

`null` は「まだ書き分けていない」の意味になるので、**残っていたら未整備**と考えること。

実例:
- `japan_vlog.color_stroke` は「縁取り無しと明記」＝ `"none"` が正しい
- `wipe_explainer.color_stroke` は「濃色縁取りだが濃色を黒と断定できない」＝ `"未計測"`
- `business_talk.color_stroke` は caption_font が「黒フチ12px」と明記済み＝ `"#000000"` で確定していた
  のに null のままだった

`color_shadow` は全15ファイルで null だったが、これは
[environment-notes.md](../environment-notes.md) の確定仕様（offset 4,4px・blur 3・不透明度40%）
が写されていなかっただけで、実際は `"rgba(0,0,0,0.4)"` が共通デフォルト。
**共通デフォルトも各ファイルへ明示する**（別ファイルを探しに行かせない。
逸脱するスタイルは `"none"` と書けば差分が見える）。

## 訂正: `mutually_exclusive_with: all` は誤りだった（2026-07-27 同日中に撤回）

同日午前に「全画面カードには `mutually_exclusive_with: all` を書く」と規定したが、
**この規定は誤りである**。documentary_investigative の再実装検証が実測で反証した。

検証者は厳格解釈（常駐要素を時間分割で消す）と緩い解釈（z_orderで覆うだけ）を
同一クリップで作り分けて出力を比較した。結果:

- statement_card区間（厳格）: watermark領域 = `[[0,0,0]]`
- endcredit区間（緩い）: watermark領域 = 同フレームの空白背景と**1画素も違わない**

**両解釈の出力が完全に一致した。** つまりこのフィールドは実装を変えず、
どちらを採ったか出力から検証できない。**inert（何もしない）フィールド**だった。

決定的なのは、**排他宣言を持たない `motion_graphic`（`style: フルスクリーン`・z=2）も
常駐watermarkを3秒まるごと消した**こと。宣言した2つと宣言していない1つで挙動に差が無い。
遮蔽は実際には `mutually_exclusive_with` ではなく **「全画面かつ不透明」＋ z_order** で
決まっており、フィールドがその事実を表していなかった。

### 正しい書き方

**遮蔽（occlusion）と排他（exclusion）を分ける。**

| 事象 | 何で決まるか | 書くフィールド |
|---|---|---|
| 全画面の不透明カードが下を隠す | 全画面＋不透明＋z_order。**自動的に起きる** | `opaque_fullscreen: true` |
| 2つの要素が同時に出ると両方読めなくなる | 座標の競合。**自動では防げない** | `mutually_exclusive_with: <role>` |

- `opaque_fullscreen: true` は**その要素自身の性質**であり、フレームを見れば検証できる。
  実装者への意味は「この要素の下は描画を省略してよい」。
- `mutually_exclusive_with` は**関係**であり、`all` のような曖昧なスコープを取らせない。
  必ず具体的なrole名を書く。

### 常駐要素が覆われるのか残るのかは、定義できていない

`watermark` のような `persistent: true` の要素と全画面カードが同時刻に来たとき、
**どちらが譲るのかを決める規則がどのスタイルにも無い**。しかも参考動画での実挙動が
yamlに記録されていないため、**そもそも正解が持たれていない**。
新規登録時は「全画面カード表示中に常駐ロゴが残るか」を必ず実素材で確認して記録すること。

### z_order が同値のときの規則

実測で `caption = watermark = 1`、`nameplate = motion_graphic = 2` のように
**z_orderの重複があるのに同値時の規則が無い**ことが判明した。
同値は「同時表示されないから競合しない」場合にのみ許す。
同時表示されうるなら**必ず異なる値を振る**。

## `centerX` のはみ出しも検算する（2026-07-27 追加）

§5 のposition解釈規約は **centerY しか規定していなかった**。
その結果 documentary_investigative で evidence_heading が左に **286px**、
caption が **63px** 切断された。QCは画面境界を見ないので目視でしか見つからない。

**検算式（centerYと同じものをXにも適用する）:**
```
centerX×1920 − 幅/2 − フチ幅 ≥ 0
centerX×1920 + 幅/2 + フチ幅 ≤ 1920
```
満たさない場合は centerX を寄せるか `max_width_px` で幅を縛る。
`ticker` のように画面端に寄せる要素は、**本来の意味が「端からのマージン」**であって
「中心の比率」ではない。実装は端アンカーで組み、centerX はその近似値として扱うこと
（entertainment_variety の ticker が centerX 0.22 で左に見切れた実例あり）。

## 「未計測」だけでは実装できない。既定値もセットで書く（2026-07-27 追加）

秒数を `entrance_sec: 未計測` と書いた結果、**文字列なのでフィールド化していないのと
同じ**になった。特に `entrance: fade` + `entrance_sec: 未計測` は下界も上界も無く
情報量がゼロで、検証者は0.5秒を発明したが「0.3でも1.5でもyamlに反しない」状態だった。

**秒数フィールドは必ず数値を入れる。** 未計測であることは注記で表す。

| 入退場 | 既定値 | 根拠 |
|---|---|---|
| `hard_cut` / `pop` | `0` | 即時。実測でフェード痕跡なしと確認されているケースが多数 |
| `fade` | `0.35` | 未計測時に採用する共通既定値 |

```yaml
entrance: fade
entrance_sec: 0.35   # 未計測。共通既定値を採用（実素材で要確認）
```

実測値がある場合はそれを書き、注記に「実測」と明記する。
`color_roles` の三値化と違い、**秒数に「未計測」という値は許さない**。
色は「描かない」という選択肢があるが、秒数は必ず何らかの値で描画されるため、
書かなければ実装者が黙って発明することになる。

## `size` と `layer_kind`（2026-07-27 追加）

### `size: {width, height}` — 寸法を書く

再実装検証8本すべてで「**寸法フィールドが1つも無く、実装者が全部発明した**」と
報告された。特に致命的だったのは全画面カードで、screen_tutorial の title_bar は
「全画面カード」と散文で書かれているのに実装では**画面の31.4%しか覆わなかった**。

- **`opaque_fullscreen: true` を名乗るなら `size` で全画面を示す**こと。
  overlap_qc は被覆率98%未満の宣言を却下する（宣言だけの独り歩きを防ぐため）
- 全画面でない要素も、衝突検算に必要なら `size` を書く。
  **要素幅が未定義な限り、中心間距離は安全の根拠にならない**
  （documentary_investigative が「768px離隔なら衝突しにくい」と書いた予測は
  実測で反証され、見出しグリフの29.27%が潰れた）

### `layer_kind: video` — QCの盲点に落ちるroleを可視化する

`overlap_qc.py` は**動画レイヤーを検査対象から除外する**（アルファを静的に取れないため）。
screen_tutorial の検証では生成20レイヤーに対し element_count=19 となり、
**PiP絡みの衝突8件がQCに1件も現れなかった**。QCのFAILだけ直すと「解決した」と
誤判定する構造だった。

盲点の存在は qc-gates.md に既知として書いてあったが、
**「どのroleが盲点に落ちるか」がyamlから読めなかった**。
動画を素材とするrole（webcam PiP・ワイプ・別撮り映像のインセット窓）には
`layer_kind: video` を付け、**必ずフレーム目視で確認する**対象だと明示すること。

## 検算は4辺すべて。上端の穴を塞ぐ（2026-07-27 追記）

position解釈規約は当初 **下端しか規定しておらず**、centerXを足した後も
**上端が抜けていた**。educational_explainer の running_outline が
**上へ28pxはみ出し、木製フレームの上辺が丸ごと欠落**して初めて発覚した。

**4辺すべてを検算する:**
```
上: centerY×1080 − 高さ/2 − フチ幅 ≥ 0
下: centerY×1080 + 高さ/2 + フチ幅 ≤ 1080
左: centerX×1920 − 幅/2  − フチ幅 ≥ 0
右: centerX×1920 + 幅/2  + フチ幅 ≤ 1920
```
`centerY` が 0.15 未満、または 0.85 超のroleは特に危ない。
`centerX` が 0.2 未満、または 0.8 超も同様。

## 中心と端を取り違えない（2026-07-27 追記・実害あり）

educational_explainer の z_order_policy は
「definition_pill下端866 / category_box上端940 → 十分な余白がある」と書いていたが、
**940 は中心であって上端ではない**。半分の高さぶんを取り違えていた。
実測では下端927 / 上端836 = **91pxの衝突**。

さらに、この2つは **どう実装しても最低37.4px衝突する**ことがフォントメトリクスから
確定した（同ファイルの caption_font が見出し104px+本文92px+フチを課すため、
高さの下限が309pxになり、866pxに必要な220pxを達成できない）。
**排他フラグが真因を隠す絆創膏になっていた。**

検算を書くときは必ず「中心±高さ/2」の形で書き、**中心の値をそのまま端として扱わない**こと。

## 全画面カードは「レンジ」で書けない（2026-07-27 追記）

educational_explainer の title_bar は `opaque_fullscreen: true` を持ちながら
`size` が無く、caption_font が許す「2-4文字」レンジで実装すると
**被覆率16.3%〜28.8%で、どれを選んでも98%に届かない**。
business_talk の title_bar は **14.4%**、screen_tutorial は **31.4%** だった。

→ `opaque_fullscreen: true` を書くなら `size: {width: 1920, height: 1080}` を必ず併記する。
書けないなら宣言を外す。**宣言だけでは1ピクセルも覆えない。**

## 検算式にドロップシャドウを入れる（2026-07-27 追記・常時7px過小評価していた）

4辺の検算式は「幅/2 + フチ幅」までしか見ておらず、**ドロップシャドウ項が抜けていた**。
[environment-notes.md](../environment-notes.md) の確定仕様は
**offset 4,4px・blur 3** なので、右と下は **4+3 = 7px** 余分に張り出す。
つまり従来の式は右下方向を**常時7px過小評価**していた。

```
上: centerY×1080 − 高さ/2 − フチ幅 − 3（影）      ≥ 0
左: centerX×1920 − 幅/2  − フチ幅 − 3（影）      ≥ 0
下: centerY×1080 + 高さ/2 + フチ幅 + 12（影）    ≤ 1080
右: centerX×1920 + 幅/2  + フチ幅 + 12（影）     ≤ 1920
```

**【2026-07-27 再訂正】当初この式の影を「右下に7px」としたが、実測で足りなかった。**
`offset 4,4px + blur 3` から素朴に 4+3=7 と計算したが、Pillowのぼかしは
**半径以上に広がる**ため実測は **右下 +11〜12px**。
さらに**ぼかしは左上にも広がる**ので **−3px** の項が要る（当初の式には左上の項が無かった）。
安全側に倒して右下12px・左上3pxを採る。

影を使わないrole（`color_shadow: "none"`）では、右下12px・左上3pxの影項を加えない。

## 「画面高の◯分の1」は何を測るのか（2026-07-27 追記）

wipe_explainer の keyword は「1-2文字が**画面高の1/3-1/2**」と実測されているが、
**何を測った値なのかが書かれていなかった**ため、同じ実装で合否が反転した:

- 文字面（グリフ）のみ = 450px（41.7%H・範囲内）
- 袋文字のフチ込み = 578px（53.5%H・**範囲外**）

**比率で書く寸法は「グリフの実高」を基準とする**（フチ・影・座布団は含めない）。
装飾を含めた外形は `size` で別に書くこと。

この取り違えは caption_font の記述にも波及していた。
「1080pなら360-540px相当」と書いたが、**font 360px のグリフ実高は342px＝31.7%H**で
「1/3以上」を満たさない。グリフ基準で1/3-1/2を満たすのは **約378-567px**。
**フォント指定値とグリフ実高は違う**ので、比率制約から逆算するときは必ず
`getmetrics()` の実測を通すこと。

## 時間区間は半開区間 [t0, t1) とする（2026-07-27 追記・実害あり）

**モード切替の時刻セマンティクスがどこにも書かれていなかった。**
ai_tool_avatar の再実装で、ffmpeg の `enable='between(t,t0,t1)'` が**閉区間**のため
**frame 330（t=11.000s）でモードA一式とモードB一式が1フレーム同時表示**された。
`mutually_exclusive_with` を宣言していても、境界の1フレームで破れる。

さらに深刻なのは、**検証者が書いたセルフチェックは開区間比較だったため
「同時表示0件」と報告した**こと。**検査は緑、出力は違反**という状態だった。

- **区間は `[t0, t1)`（開始を含み終了を含まない）とする**
- ffmpeg の `between()` は閉区間なので、終了側は `t1 - 1/fps` を渡すか
  `lt(t,t1)` を使う
- **排他の検査は必ず実フレームで行う**。区間の突き合わせだけでは境界を見逃す

## `persistent: true` は変種・モードのスコープ内での常駐（2026-07-27 追記）

同一role名が変種違い・モード違いで2エントリある場合、**両方が `persistent: true`
を持つと、フィールドを素直に読んだ実装者は両方を全編表示する**。
ai_tool_avatar では大小2匹のネコが30秒間同時に出て、矛盾を解いたのは
`variant` でも `mutually_exclusive_with` でもなく**散文（dual_mode）だけ**だった。
wipe_explainer の PiPパターンA/B も同じ構造。

- `persistent: true` は「**その変種・モードが有効な区間の中では常駐**」の意味とする
- 全編での常駐を意味するのは、`variant` を持たないroleに限る
- 変種を持つroleに `persistent: true` を書くときは、この注記を必ず添えること

## `anchored_to_target` は「対象の入力経路」がないと機能しない（2026-07-27 追記）

`position_mode: anchored_to_target` を付けただけでは実装者は何もできない。
ai_tool_avatar の keyword は「この入力欄に注目してください」というナレーションの横で
**無関係な窓枠と人物の顔を赤枠で囲んだ**。documentary_cinematic でも
keyword が棒グラフを91.8%被覆しており、**同じ構造が2スタイルで未解決**。

`anchored_to_target` を書くなら、最低限これも書く:
- `anchor_targets`: 指し示す対象の種類の列挙（例: 入力欄 / ボタン / 表の行 / 棒グラフの棒）
- 対象座標をどこから得るか（素材のメタデータ / 実装時に人が指定 / 画像認識）
- 枠の寸法規則（対象のbboxに対するパディング）

これらが無い場合は `position_mode: anchored_to_target` **だけを書いて満足しない**こと。
「座標は可変」と宣言しただけで、実装者が正しく置ける保証は何もない。

## 常時表示が要求されるroleを排他の対象にしてはいけない（2026-07-27 追記・実害あり）

ai_tool_avatar の caption（発話追従の字幕）に
`mutually_exclusive_with: [sidebar, nameplate]` を書いたところ、
**structure_grammar.dual_mode と両立しなかった**。

- dual_mode に従うと **684/900フレーム＝76.0%が排他違反**
- 排他に従うと **caption が全編どこにも出せない**
  （sidebar はモードA主軸、PiP はモードB常駐のため）

発話中の4秒が字幕なしになる区間が実演で確認された。

**排他は「どちらかを出さなくてよい」ペアにしか使えない。**
常時表示・発話追従が要求されるrole（字幕・常駐ロゴ等）が相手と重なるなら、
**排他ではなく幾何で解く**（相手に `size` を与えて帯域を空ける）。

また、**role名で一括指定すると変種・モード違いの全エントリにかかる**点に注意。
上記の例では mode_A が340.6px衝突・pixel 1.0 なのに mode_B は60.9px余白で
衝突なしと**実態が正反対**だったのに、role名指定が両方にかかっていた。

## 排他は必ず両側に書く（2026-07-27 追記）

片側だけの宣言は、もう一方のroleだけを読んだ実装者に伝わらない。
機械照合で6件の非対称が見つかり、うち1件は
**実測でCTAの価格+URL帯を58.5%潰した組み合わせ**だった
（CTAカード側だけ読むと「字幕と同時に出してよい」と判断してしまう）。

**過剰宣言もしない。** 幾何交差がゼロのペアを排他にすると、実装の自由度を
理由なく削り、宣言そのものの信頼性が下がる（documentary_narrated_jp で1件訂正した）。

## 幅を縛るときは行数も同時に縛る（2026-07-27 追記・3スタイルで同じ失敗）

`max_width_px` だけを設定すると**行数が増えて事態が悪化する**ことがある。

- japan_vlog: 1875px→1500px にしたら 3行31px侵入 → **4行86px侵入**へ悪化
- wipe_explainer: caption の幅指定で PiP との重なりが 15.9% → **31.0%** へ拡大
- wipe_explainer: sidebar が1行→2行で高さ154→258px、PiP重なり 0.5% → **9.4%**

**`max_width_px` と `max_lines` は必ずセットで書く。**
そのうえで `max_chars × max_lines` が実素材の発話長を下回るなら、
**字幕を長くするのではなく発話の区切りで複数イベントに分割する**。

## `max_lines` は幾何と突き合わせて決める。既定値を配ってはいけない（2026-07-27 追記・退行を作った）

「幅を縛るなら行数も縛る」と規約化したあと、**私は role名の慣習（見出し=1行/字幕=2行）で
20roleへ機械的に配った**。幾何を見ていなかったため、**検証で「可」だったスタイルを1本退行させた**。

`documentary_immersive` の B3 caption は `max_chars: 9`（9字=828px / 10字=920px>900）で
**1行しか成立しない設計**なのに `max_lines: 2` を付けた。同ファイルの z_order_policy は
「2行字幕は幾何的に成立しない／解は max_chars:9 の遵守」と書いており、**同一ファイル内で
正面から矛盾**した。実測で14字2行は名札を pixel 98.87% で潰した。

→ **`max_lines: 2` は安全上限ではなく、破綻状態にだけ効く許可証になりうる。**
`max_chars × フォント幅 ≦ max_width_px` なら**その role は1行設計**であり、2を書いてはいけない。
同じ誤りが `ai_biz_pitch.base_caption`（20字×92=1858px）と `ai_tool_avatar.caption`
（12字×92=1104px＝max_width_pxと完全一致）にもあった。

**掃引条件の穴**にも注意。`max_chars` も `max_width_px` も持たない role は
一括補完の対象から**構造的に外れる**（`educational_explainer.region_card` が
幅の議論から外れたまま37px切断を残していた）。

## 座標の導出は `max_lines` の最大値で行う（2026-07-27 追記）

`ai_biz_pitch` の座標修正3件は「字幕1行＝上端866px」前提で導出したが、
同ファイルの `max_lines: 2` を使うと上端799pxになり**3件とも衝突した**。
`documentary_investigative.nameplate` の 0.81 も、
`documentary_narrated_jp.person_nameplate` の 0.67 も同じ壊れ方をした。

**行数を後から足したら、その role に依存する全座標を導出し直すこと。**

## 導出に使った寸法は必ず `size` に書く（2026-07-27 追記）

書かないと**修正が再現しない**。`ai_biz_pitch` は3値が散文にしかなく「QCはPASSしたのに不可」と
判定された。`documentary_startup_journey` の `chapter_tag × person_status` は
導出前提の高さ（69px/109px）がフィールドに無かったため、再実装で83/144pxになり
**pixel_collision 0.968 で衝突が復活**した。

## 4辺検算は「クリップ前の名目bbox」で測る（2026-07-27 追記）

1920×1080のキャンバスに描くと、**画面外へ出た分をPillowが黙って切り落とす**。
その後のbboxを見ると `L=0` が返り、**検算が「OK」と誤答する**。
`documentary_startup_journey.person_status` の左15.9pxはみ出しはこの型で、
QCも画面外を見ないため**目視でしか発見できなかった**。

→ 検証時は**四方に余白（400px程度）を付けたキャンバスで描画し、
切り取り前の名目bboxと4辺のはみ出し量を測る**こと。

## `max_width_px` は「折返し幅（テキスト領域の幅）」（2026-07-27 追記・解釈で結果が反転した）

`educational_explainer.region_card` の検証で、**同じ値が解釈次第で真逆の結果**になった。

- schema.md準拠（**折返し幅**）と読むと 1033px < 1100 で折り返さず、**左37px切断が再現**
- yaml注記準拠（**カード外形幅**）と読むと2行化して**左余裕+101pxで解消**

**定義を確定する: `max_width_px` は折返し幅＝テキストが折り返される幅**であり、
座布団・パディング・縁取り・影は**含まない**。

外形の幅を縛りたいときは `size.width` を使う。両方書く場合の関係は
`size.width ≥ max_width_px + padding×2 + フチ×2` である。

**この2つを混同すると、切断するかしないかが変わる。** 座標の導出に使うのは
必ず `size`（外形）の方で、`max_width_px` は折返しの計算にだけ使うこと。

## `max_chars` は行数を縛らない（2026-07-27 追記・私の判定が誤っていた）

`documentary_immersive` の破綻を「max_chars: 9 の遵守で防げる」と書いていたが、
**これは誤り**だった。14字「今日は波が高いので気をつけて」を折り返すと
`['今日は波が高いので'(9字), '気をつけて'(5字)]` となり、
**各行9字以下＝max_chars を1文字も違反していない**。

schema.md は `max_chars` を「**1行あたり**の上限」と定義しているので、
**文字数をいくら縛っても行数は止まらない**。あの破綻を止めている唯一のフィールドは
`max_lines: 1` である。

→ **「max_chars を守れば安全」と書いてはいけない。** 行数の制約は `max_lines` にしかない。
（私は「max_chars:9 は遵守で被覆0.0%／違反で99.1%」と報告したが、
その検査コードが行数条件を混ぜていたための誤りだった。）

## 寸法だけ書いてフォントを書かない（2026-07-27 追記）

`documentary_immersive.logo_badge` に `size: 380x58` を与えて上端切断は直ったが、
**58pxに散文どおり2段を収めるとロゴ27px・副題6pxまで縮み、1080pで副題が判読不能**に
なった。切断は消えたが読めなくなったので、実質的な改善になっていない。

`size` を書くときは、**その箱に何を入れるつもりかをフォントサイズで示す**こと
（`font_px` / `font_px_attr` / `font_px_name` 等）。
箱だけ決めると実装者が中身を潰して収める。

## 4辺検算は `opaque_fullscreen` を除外する（2026-07-27 追記・3度指摘された偽陽性）

`size: {1920, 1080}` の全画面カードに影の項を足すと、**定義上必ず
「上3 / 下13 / 左3 / 右13 はみ出し」**になる。3スタイルで同一の偽陽性が再現した。

- **`opaque_fullscreen: true` の role は4辺検算の対象外**とする
- 全画面カードは「画面を覆う」のが仕事なので、はみ出しは仕様である
- ただし**装飾を意図的に画面外へ流す実装**（ai_news_weekly sidebar が L=−1/R=2042）も
  同じ形で出るため、`opaque_fullscreen` でない role のはみ出しは必ず精査すること

除外しないと**全画面カードが永久にNGを出し続け、本物のはみ出しが埋もれる**。

## 検算式は「自分が書いた式」と「自分が書いた値」を突き合わせる（2026-07-27 追記）

`documentary_startup_journey.cta_banner` は `size: 900x282` の隣に
`(801 − 16 − 12 − 648) × 2` と式を書いているが、**この式は250にしかならない**。
282を逆算すると `(801 − 12 − 648) × 2` で、**16pxの余白項が自分の計算から落ちていた**。

実害: CTAの実下端がちょうど801pxに来て、字幕まで3pxしか残らない（衝突はしない）。
**式と値が合っていないと、次に触る人がどちらを信じればよいか分からない。**
値を書いたら、その場で式に代入して検算すること。

## `max_lines: 1` のとき、超過テキストは折り返さず**イベントを分割する**（2026-07-27 R4追記）

`ai_tool_avatar.caption` は `max_lines: 1` と `max_chars: 11` を持つのに、
12字・14字の発話が **max_chars を1文字も違反しないまま2行になった**（各行8字/10字）。
折返し器が11字で改行すると、**結果の各行は11字以下なので max_chars は満たされる**。

**`max_chars` は行数を止めない**（既出）だけでなく、
**`max_lines: 1` との併用でも止まらない**。実装者が「折り返す」を選ぶ限り破れる。

→ **`max_lines: 1` の role では、`max_chars` を超えるテキストは
折り返さずに複数のテロップイベントへ分割する**と明記すること。
「収まらないなら分ける」であって「収まらないなら折り返す」ではない。

これは発話の区切りを編集側で決める作業であり、レンダラの自動折返しに任せてはいけない。

## フィールドを直したら、そこから導いた値を**全部**やり直す（2026-07-27 R4追記）

規約は「値を書いたら式に代入して検算する」という**順方向**しか書いていなかった。
R4で見つかった3件はすべて**逆方向の欠落**、つまり
**1箇所だけ直して派生値を更新しない**型だった。

| 直したもの | 更新し忘れた派生値 | 結果 |
|---|---|---|
| `logo_badge` に font_px_logo 48 / sub 26 を追加 | `size: 380x96` | 実寸の行高は **70+39=109px**（padding 0 でも13px超過）、幅も副題396px > 内幅356px。**副題が座布団の外に出て素の映像の上に乗った** |
| `region_card` の関係式 `1120 = 1000+48+72` | **国旗アイコンの幅を1pxも含んでいない**（emphasis_roles は「国旗アイコン+ラベル」と明記） | 内容から外形を算出すると左27px切断 |
| 影の項を 7→12 に訂正 | 同じ行の**和**（`907.2+128+11.5+7=1053.7` と `11.5+7=18.5`） | 数字だけ替えて和が古いまま＝同じ行の中で算術が破綻 |

**チェックリスト（フィールドを1つ変えたら必ず全部見る）**
1. その値を使っている**同じroleの他フィールド**（font ↔ size ↔ max_width_px ↔ max_lines）
2. その値を引用している**同じファイルの散文**（z_order_policy / apply_notes / caption_font）
3. その値から導出した**他roleの座標**（隣接要素のクリアランス）
4. コメント内に書いた**計算式の和**（項を変えたら合計も変わる）

**特に「フォントを足したら size を検算し直す」「size を書いたら中身が入るか確かめる」**。
箱と中身のどちらか一方だけ決めると、必ずもう一方が破綻する。

## role の `font_px` は `caption_font` より優先する（2026-07-27 R5追記・真因はこれだった）

`business_talk.nameplate` は **R2〜R4の3周にわたり同一の衝突

真因は個別の数値ではなく、**「role の `font_px` と `caption_font` のどちらが優先するか」
という規約が存在しなかった**こと。`sidebar` にだけ「caption_font を適用禁止」の一文が
あり、`nameplate` と `question_tab` に無いのは**規約ではなく偶然**だった。

- **role に `font_px`（または `font_px_*`）があれば、それが `caption_font` の記述に優先する**

  「このroleは font_px を参照」と書き添えて矛盾を可視化すること

個別roleに数値を足すだけでは解けない種類の欠陥だった。

## 検査を黙らせる修正をしない（2026-07-27 R6追記・実際にやった）

- 除外条件のある検査は、**除外に該当させる修正**で簡単に騙せる

## 規約の掃引は「機械照合を書く」までがワンセット（2026-07-27 R6追記・退行を出した）

**【2026-07-27 訂正】「documentary_immersive が退行した」という私の当初の診断は誤りだった。**

## 検査自身の絞り込みが、検査の目的を殺す（2026-07-27 R8追記）

R8で lint のバグを**4件**見つけたが、4件とも同じ形だった:
**「その欠陥を捕まえるために作った検査が、絞り込みのせいでその欠陥を見逃していた」。**

| 検査 | 絞り込み | 見逃したもの |
|---|---|---|
| 括弧の対応 | `if "#" in l` でコメント行だけ | ブロックスカラーの散文。**この検査を作る理由だった実欠陥**（開き83/閉じ84） |
| 排他の対称性 | `decl[role]` で同名エントリをマージ | 同名2エントリの片方の欠落（cinematic の sidebar[A3]） |
| フォント解決 | `font_px` / `font_px_max` のみ | `font_px_en` / `font_px_ja` を持つ二段role → 既定92に落ちて偽陽性 |
| centerY の追随 | 履歴語を**その1行**で判定 | 「**旧記述**:」の続きの行 → 偽陽性 |

**絞り込みを書いたら、「この条件で落ちるのは何か」を1回声に出す。**
とくに `if 〜 in line` のような行単位フィルタは、複数行にまたがる対象を必ず落とす。

検査を足したら、**除外条件を一時的に外して流し直し、件数が増えることを確かめる**
（増えなければ、その検査は何も見ていない）。

## 袋文字ではフチ幅も `size` の「中身」である（2026-07-27 R8追記）

規約「`size` を書くときは、その箱に何を入れるつもりかを `font_px` で示す」だけでは

## 矩形が重なるなら position が違っても危険（2026-07-27 R8追記）

## 欧文roleは `char_width_px` が無いと `max_chars` が必ず過剰になる（2026-07-27 R9追記）

幅の検算は既定で「全角1字＝`font_px`」を使う。欧文キャップスのroleにこれを当てると、
**実力の半分に縛る値**になる。

narrated の `bilingual_nameplate` は R8 で `max_chars: 25` を入れたが、

和文が律速するroleでも、**`char_width_px: <font_px>` を明示的に書く**。
既定と同じ値だが、「見落としたのか、全角でよいのか」が次の実装者に伝わる。

**規約を足した周のうちに検査を書く。検査を書かない規約は、書いた本人が翌周に破る。**

## 派生値は「分母を動かした周」で全部やり直す（2026-07-27 R9追記・私の事故）

R8 で ai_biz_pitch の `base_caption` を 0.85 → 0.81 に動かしたとき、
**その値を分母にして導出されていた4roleを1つも追随させなかった**:

| role | ずれ |
|---|---|
| `reaction_character` | −41px（字幕に食い込む） |
| `promo_cta_banner` | −37px（実インク3.2%消失・QC FAIL・目視で枠線が断ち切られる） |
| `positive_keyword` | +2px |
| `highlight_marker` | 字幕に乗る装置なのに 0.85 のまま（43.2pxずれ） |

しかも `promo_cta_banner` の `size.height 720` という値自体が、
**旧 `base_caption` から導出されたもの**だった。座標だけでなく**寸法も派生値**である。

座標や寸法を動かしたら、`grep` でそのroleを参照している導出を全部洗う。
「この値を分母にしているのは誰か」は lint では出せない（導出は散文にある）ので、
**注記に「この値は ○○ から導出した」と必ず書く**。それが唯一の検索キーになる。

## 4辺検算は「必須」と書いただけでは実行されない（2026-07-27 R10追記）

この規約は R3 から本文にある。にもかかわらず**機械照合を書いたのは R10 が初めて**で、
書いた瞬間に **16件**が出た。R9 までに実際に出した実害は次のとおり:

| 周 | 実害 |
|---|---|
| R9 | cinematic の全画面図解が**上端 −15.5px**（導出が下端しか解いていなかった） |
| R9 | ai_biz_pitch の煽りテロップが**下端ちょうど1080px**（余裕ゼロ） |
| R9 | startup の章タグが**上端7px**、しかも注記は「左端7pxを解消」と書いていた |
| R10 | kirinuki のロゴが上端3px。**同じブロックが「境界解・上端の余裕3.0px」と
自認する注記を持ちながら、値は直っていなかった** |

最後の1件が本質を示している。**人は「気づいて注記を書く」ところまではやるが、
そこで満足して値を直さない。** 機械は注記を読まないので、値が直るまで鳴り続ける。

**「必須」と書く規約には、その周のうちに検査を書く。** 書けないなら「守られない」と
明記して運用する。R3 から R10 まで7周、この規約は本文にあるだけだった。

画面端にフチ合わせで置くのが設計の装置（レターボックスの黒帯、隅に接する円形PiP）は
`edge_bleed: true` で明示的に除外する。**推測で除外しない**——
「たぶん端に付けたいのだろう」で外すと、検査の意味が消える。

## `max_chars` は1行の上限。総量は `max_chars_total` で別に決める（2026-07-27 R10追記）

**`max_chars × max_lines` は総量の上限にならない。**
investigative の `evidence_heading` は名目 17×2 = 34字だが実容量は **29字**で、
**yaml自身が例示する33字の文言が3行になり、3行目と赤下線が黒座布団の外へ93px出て
素の映像に載った**（QCは exit 0 で素通り。目視でしか見つからない）。

名目と実容量が割れる原因は2つだけである:

1. **欧文は単語の切れ目でしか折り返せない**。平均送り（`char_width_px`）は
   幅の検算には使えても、容量の保証にはならない
2. **`max_width_px ÷ char_width_px` の端数を切り捨てる**と、行ごとにその端数を損する

和文ベタ（どの文字でも折り返せて端数も出ない）なら掛け算がそのまま総量になる。
`check_max_chars_total` はこの2条件のときだけ鳴る。

## 「実測」と書くだけでは実測にならない。文字列・px・字数の3点を書く（2026-07-27 R10追記）

同じ周に足した2つの `char_width_px` で、片方だけが効いた。

```yaml
bilingual_nameplate:
  char_width_px: 27   # 実測 1099px / 42字 = 26.17px（切り上げ27）   ← 効いた
bilingual_caption:
  char_width_px: 32   # 上段の英語原文キャップス（font 56）の実測送り幅  ← 効かなかった
```

後者は独立実測で 32.36 / 32.56 / 34.22 px/字（実在しうる英文3本）と判明し、
宣言が主張する「余裕24px」は存在せず**3本中2本が折返し幅を超えた**。

**差は「測った文字列・実幅px・字数」を書いたかどうかだけ。**
それが無い数値は、次の人にとって検証不能であり、書いた本人にとっても再現不能である。

## 影の張り出しは閾値で変わる。画面外判定は `alpha > 0` で見る（2026-07-27 R11・独立実測）

R11 の検証者が「schema.md の +12 / −3 は過大で、実測は右下+8・左上±0」と報告したので、
確定仕様（offset 4,4 / blur 3 / α40%）で自分でも測り直した。

| 閾値 | 右下 | 左上 |
|---|---|---|
| `alpha > 0`（目に見える範囲） | **+11** | **+3** |
| `alpha > 10`（`overlap_qc` のトリム閾値） | +8 | 0 |

**両者は矛盾していない。閾値が違うだけである。**
検証者は QC 閾値で測っていた。

- **QCの交差判定は `alpha > 10`**（ツールがそこでトリムするため）

過大ではない。据え置く。**ただし注記に「どの閾値の値か」を書いていなかった**ので、

## `overlap_qc` の pixel_collision が11周ずっと狂っていた（2026-07-31・外部PRで発覚）

**1. アルファ切り出しのオフセット漏れ（重い）**

```python
lx0, ly0 = ix0 - el.x, iy0 - el.y            # 旧
```

`Element.x/y` は**透明余白をトリムした後**の画面座標なのに、読み込む配列は**元PNG全体**。

交差の有無（bbox）は正しいので結論の多くは変わらないが、
**「pixel が高いから実害」という判断は測り直すまで保証されない**。

**2. 画面外の面積を被覆に数えていた**

```python
cover = (el.w * el.h) / (CANVAS_W * CANVAS_H)   # 旧
cover = canvas_coverage(el, CANVAS_W, CANVAS_H) # 新（画面内の面積だけ数える）
```

画面からはみ出した要素が「98%覆っている」と主張でき、`opaque_fullscreen` の

## キャンバスは「回転後」の寸法で決める。全15スタイルは横前提（2026-08-01・実素材で判明）

`ffprobe` の `stream=width,height` は **回転メタデータを適用する前**の値である。
iPhone の縦撮りは `stream_side_data=rotation=-90` を持ち、**ffmpeg は自動で回転を適用**する。

```
ffprobe が返す寸法 : 1920x1080
実際のキャンバス   : 1080x1920（縦）
```

これを読み違えると、**座標系が丸ごとずれる**。実際に字幕を 1920x1080 前提で作り、
1080幅のキャンバスに載せて**右端が切れた**（`work/frames/out12.png` で目視確認）。

```python
rot = probe("stream_side_data=rotation")
r = abs(int(float(rot))) % 180
W, H = (h, w) if r == 90 else (w, h)     # ← これがキャンバス
```
