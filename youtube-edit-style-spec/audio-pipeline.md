# 音声パイプラインの制約（LUFS/LRA/無音率）

**このファイルは何を扱うか**: ラウドネス正規化（LUFS）とダイナミックレンジ（LRA）が同時に満たせないという実測結論、および「間を残す」設計スタイルで無音率が構造的に潰れる根本原因と正しい手順。
**いつ読むか**: スタイルの音響目標（LUFS/LRA/無音率）を設計・検証する工程。音声強調・ASR側の手順は [captions-quality-v2.md](captions-quality-v2.md) を参照。True Peak実測やAPIパスの音声処理は内部の運用文書を参照（公開版には含めない）。

## LUFSとLRAは同時に満たせない（2026-07-27に実測で確定・「2パスにすれば直る」は誤り）

適用検証12本のうち**6本がLUFS/LRA未達**で、複数のレポートが独立に
「single-pass dynamic loudnormの限界。**2パス方式で改善余地あり**」と推測していた。
**実測して検証したところ、この推測は誤りだった。**

`DJI_0029/work/audio_16k_mono.wav`（I=-33.0 / LRA=9.1 / TP=-11.2）で3方式を比較:

| 方式 | LUFS | LRA | 備考 |
|---|---|---|---|
| A: 単一パス dynamic loudnorm | -17.1 | 4.1 | 従来 |
| B: **2パス linear loudnorm** | **-17.1** | **4.1** | **Aと完全に同一。改善しない** |
| C: 単純ゲイン + リミッター | -17.5 | **6.0** | **LRA保存では最良** |

**2パスにしても結果は1ミリも変わらない。** loudnormのlinearモードは
「測定値を渡して同じ変換を再現する」ものであって、ダイナミクスを回復するものではない。

**本当の制約はゲインとLRAの線形な交換関係**（192kHzオーバーサンプリングのリミッター使用時・TPは常に-2.5で安全）:

| ゲイン | LUFS | LRA |
|---|---|---|
| +18dB | -17.9 | 5.4 |
| +19dB | -17.3 | 5.0 |
| +20dB | -16.8 | 4.6 |
| +21dB | -16.3 | 4.2 |
| +22dB | -15.8 | 4.0 |

**LUFSを1LU上げるごとにLRAが約0.9LU潰れる。**
したがって `business_talk` の目標（LUFS -15.4 / LRA 5.7）はこの素材では**同時達成不可能**。

**運用方針**:
1. **どちらを優先するかをスタイルごとに決める**。無音率と同じく、LUFSとLRAは独立に満たせる値ではない
2. **LRAが広いスタイル（japan_vlog 19.0 / narrated_jp 10.4 等）はLRA優先**。
   単純ゲイン＋リミッター（方式C）を使い、loudnormのdynamicモードは使わない
3. **LUFSが重要なスタイル（YouTube標準-14付近を狙うもの）はLUFS優先**。LRAの縮小は許容する
4. **根本解決には素材側の改善が要る**（クレストファクタの小さい＝平均レベルの高い収録）。
   実装では超えられない

## 音声パイプラインの根本的な欠陥（2026-07-26 build_live検証で判明・必ず踏襲）

**単一パスの `loudnorm` でLUFS目標までゲインを上げると、無音区間のノイズフロアも比例して持ち上がり、-35dB閾値を超えて `silencedetect` が無音を検出できなくなる。**
＝「間を残す」設計のスタイル（ドキュメンタリー系・スタートアップ系など無音率5-30%を要求するもの）が**構造的に実装できない**。

**正しい手順**:
1. **発話部分のみ**を対象にラウドネス正規化する
2. **正規化した後で**、間の区間に**真のデジタル無音**を挿入する（ノイズフロアごと持ち上げない）
3. 書き出し後に `silencedetect -35dB/0.5s` で**目標の無音率になっているか実測して確認する**

この手順で build_live は無音率 **5.00%（目標5.01%）** を達成した。素材の自然な無音率は1.35%しかなかったため、**意図的に間を作らないと目標に届かない**点にも注意。
