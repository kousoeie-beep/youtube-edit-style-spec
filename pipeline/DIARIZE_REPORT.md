## 1. 採用した経路と根拠

### 経路①（第一候補・キーがあるときに走る）

| 項目 | 値 | 出所 |
|---|---|---|
| モデルID | `gpt-4o-transcribe-diarize` | https://developers.openai.com/api/docs/guides/speech-to-text |
| エンドポイント | `POST /v1/audio/transcriptions` | 同上 |
| response_format | `diarized_json`（これでないと話者ラベルが返らない） | 同上 |
| chunking_strategy | 30秒超の音声で**必須**。`"auto"` または VAD 設定 | 同上 |
| segment のフィールド | `speaker` / `text` / `start` / `end` | 同上 |
| ファイル上限 | 25 MB（mp3, mp4, mpeg, mpga, m4a, wav, webm） | 同上 |
| 既知話者 | `known_speaker_names[]` / `known_speaker_references[]`（最大4人・参照音声2〜10秒） | 同上 |
| 制約 | プロンプト非対応 | 同上 |
| 料金 | **$0.006 / 分** | https://developers.openai.com/api/docs/pricing |

一次情報を実際に取得して確認した。記憶で書いた値は1つもない。
`https://platform.openai.com/docs/api-reference/audio/createTranscription` は 403、
`platform.openai.com/docs/pricing` は `developers.openai.com/api/docs/pricing` へ301。
ドキュメント本文の Python 例に `chunking_strategy="auto"` と
`extra_body={"known_speaker_names": [...], "known_speaker_references": [...]}` がある。

**注意（実測）**: `a_enh.wav` は **51.7MB で 25MB 上限を超える**。192kHz PCM のため。
`diarize.py` は超過時に自動で mp3 64k / 16kHz mono へ落とす。実測 51.7MB → **1.1MB**。

### 経路②（フォールバック・今回走ったのはこちら）

`OPENAI_API_KEY` は `os.environ` からのみ取得。`.env` は読まない。今回は環境に無かった（未設定を確認）。

- 解析単位: `librosa.effects.split` の発話区間を 2.5秒で刻む
- 特徴量: MFCC 20次の平均＋標準偏差（無音フレームは RMS で除外）→ z-score
- クラスタリング: Ward法。k は 2 を既定とし、シルエット係数が 0.02 以上上回ったときだけ 3 へ
- pyannote などの学習済み話者埋め込みは使っていない（指示どおり）

## 2. インターフェース

```python
diarize(wav_path, work_dir, segments=None) -> [{"start","end","speaker"}, ...]
assign_speakers(caps, turns)              -> caps の各要素に "speaker" を付けて返す
```

`work_dir/diarization.json` に `route` / `confidence` / `low_confidence` / `turns` を保存する。
API経路のときは生応答を `work_dir/diarization_api.json` にも残す。

CLI:
```
uv run --with librosa --with soundfile --with scipy --with numpy \
  python3 diarize.py <wav> --work <dir> --caps captions.json [--force-local]
```

### 検証したこと

- **API経路**: キーが無いため、公式ドキュメント記載どおりの `diarized_json` を模した応答を
  流し込んで解釈を確認した。送信フィールドが
  `model=gpt-4o-transcribe-diarize` / `response_format=diarized_json` / `chunking_strategy=auto` /
  `file=@...` であること、`speaker_1`→A・`speaker_2`→B と出現順にラベルが振られること、
  保存JSONに**キーが混入しないこと**を確認した。25MB超の圧縮分岐も実ファイルで動作確認済み。
- **assign_speakers**: どのターンとも重ならない字幕が直前の話者を引き継ぐことを確認した。

## 4. 話者交代の時刻は会話の切れ目と合っているか

### 4-1. 映像での目視（ffmpeg でフレーム抽出）

`/Users/kousuke/Downloads/IMG_2514.MOV` から 2〜130秒の30フレームを抜いて確認した。

**結果: 映像では話者交代を検証できない。** 素材の作りがそれを許さない。

1. **カメラを持っている人物は最後まで一度も画面に入らない。** 2人のうち片方の口元が原理的に見えない。
2. 画面に映るのは基本的に**着席した1名だけ**。カメラは終始TVの方を向いている。
3. 6.9〜12.0秒だけ、**TVに手を伸ばして指差す別人物の腕と頭**が画面右上に入る（拡大して確認）。
   ただしこれが「3人目」なのか「撮影者が空いた手を伸ばしている」のかは映像から判別できない。
   つまり**在室人数は2人とも3人とも確定できない**。
4. カメラが手持ちで動き続けるため、顔の位置が固定されず、口の開閉を追う切り出しができなかった
   （固定クロップを試したが胴体しか写らず失敗）。

したがって「2人が交互に話す対談」という前提自体、映像からは裏取りできなかった。

## 5. 精度の限界（正直なところ）

### 5-1. 13/14 は実力ではない。探索で拾った当たりくじだった

窓の置き方（位相）を **6ミリ秒**ずらしただけでスコアは 13 → 10 に落ちた。
そこで窓位相を20通りずらして平均を取り直した（実測）:

| 音源 | 窓 | k | 質問→答えの境界（4点満点）平均 |
|---|---:|---:|---:|
| a_enh（強調後） | 2.5s | 2 | **0.85** |
| a_enh（強調後） | 3.0s | 3 | 1.55 |
| a16k（生） | 2.5s | 2 | 1.30 |
| a16k（生） | 2.5s | 3 | **1.80**（全構成中の最良） |

**ラベルを完全ランダムに振った場合の期待値は約2.0。** 最良構成でも偶然と同等かそれ以下。
「全部同じ話者」と塗りつぶした場合でも合計10点が取れてしまう（MUST_SAME が全部当たるため）。
巡回シフト基準線（ラベル列の時間対応だけ壊す）は平均8.7・最大11。

**つまりこのローカル経路は、この素材では話者情報をほとんど持っていない。**

### 5-2. どこで間違えるか

- **質問と答えの境目**を落とす。実測で4組中1〜2組しか取れない。字幕に焼くと会話が入れ替わる。
- **相槌・短い割り込み**は取れない。解析単位が2.5秒あるので、それより短い発話は隣に飲まれる。
- **境界の時間分解能が粗い**。交代時刻は窓の刻み（2.5秒）に量子化される。
  上の交代時刻が 9.99 / 34.93 / 42.42 … と 2.49秒の倍数に並んでいるのはそのため。
- **後半45秒はそもそも意味がない**。10秒ブロックごとの有声フレーム率（実測）は
  0〜90秒で 26〜59% あるのに、90〜134秒では **12〜25%** まで落ちる。
  笑い声と無音が主で、話し声がほとんどない。ここの字幕自体（`ふふふふ…`×15件、
  88.10–104.52 の16.4秒1件）がASRの取りこぼしであり、話者を付ける対象になっていない。

### 5-3. なぜ効かないか（この素材固有の事情）

1. **男性2名でF0が重なる。** 区間ごとの中央値が 110〜125Hz に集中し、声の高さで割れない。
   F0とスペクトル重心を特徴に足して重み付けもしたが改善せず、最終的に**外した**。
2. **単一マイクが動く。** 手持ち撮影で近接感（音量・直接音/残響比）が話者ではなく
   カメラの動きで変わる。生音の区間RMSは -23〜-36dB の範囲で暴れる。
3. **強調処理が手がかりを消す。** `run.py` の `loudnorm` + `acompressor` により、
   `a_enh.wav` では **VADが完全に無効**になる（top_db=30 で「発話」1区間・カバー率100%）。
   生の `a16k.wav` なら136区間・91.4%。強調後の音を食わせると、本コードは実質
   「全体を2.5秒で刻んだ等間隔窓」として動く（そのことをログに出すようにした）。
4. **ステレオの空間手がかりも効かなかった。** 元MOVは2ch。左右音量差・GCC-PHAT遅延・
   相関ピークを特徴に加えて試したが、境界検出の中央値は 0.0〜2.0 で改善しなかった。

### 5-4. 他に試して駄目だったこと（記録）

- 解析単位を ASRセグメント / 既存字幕にそろえる → 13 → 10, 9 に悪化
- k-means による重心再割り当ての追い込み → 13 → 9 に悪化
- 重なり窓（hop < win）で境界分解能を上げる → 改善なし
- ケプストラム平均正規化（CMN）→ 有意差なし

### 5-5. だから何をしたか

出力に**シルエット係数を confidence として必ず付け**、0.15 未満なら
`low_confidence: true` を立てて警告を出すようにした。今回の実測値は **0.066**。
**このフラグが立っている限り、話者ラベルを字幕や納品物に焼き込んではいけない。**
使えるのは「ここで話者が変わったかもしれない」という編集者向けの当たりを付ける用途まで。
